# 安全性

Pi 是一个本地编码代理。它以启动它的用户账户的权限运行，并将该用户可写的文件视为处于同一本地信任边界内。

## 项目信任

项目信任控制 pi 是否加载项目本地的设置、资源、包和扩展。它不是沙箱，也不会限制模型在你开始在某个目录中工作后可以要求工具执行的操作。

Pi 会在当前工作目录中发现以下任一项时，认为该项目存在信任输入：

- 当前目录中的 `.pi/`
- 当前目录或祖先目录中的 `.agents/skills`

当交互式会话在包含 `.pi` 或 `.agents/skills` 配置的项目中启动，且当前目录或父目录没有已保存的决定时，pi 会遵循全局设置中的 `defaultProjectTrust`。默认值为 `"ask"`，即在有 UI 可用时询问是否信任该项目。已保存的决定按规范化目录存储在 `~/.pi/agent/trust.json` 中，当前路径或父路径上最近的已保存决定优先于全局默认值生效。

信任某个项目会允许 pi 加载受信任门控的项目输入，包括：

- `.pi/settings.json`
- `.pi` 资源，例如扩展、技能、提示模板、主题和系统提示文件
- 通过项目设置配置的缺失项目包
- 项目本地扩展和项目包管理的扩展

拒绝信任会跳过受保护的资源。除非上下文加载被禁用，否则无论项目信任状态如何，都会加载 `AGENTS.md` 和 `CLAUDE.md` 上下文文件。在信任被解析之前，pi 只加载上下文文件、用户/全局扩展和 CLI `-e` 扩展。用户/全局扩展和 CLI 扩展可以处理 `project_trust` 事件；第一个返回是/否决定的扩展拥有该决定的所有权。

非交互模式（`-p`、`--mode json` 和 `--mode rpc`）不会显示信任提示。在没有适用的已保存信任决定的情况下，`defaultProjectTrust: "ask"` 和 `"never"` 会忽略此类资源，而 `"always"` 会信任它们。使用 `--approve`/`-a` 或 `--no-approve`/`-na` 可以为单次运行覆盖项目信任设置。

## 无内置沙箱

Pi 不包含内置沙箱。内置工具可以读取文件、写入文件、编辑文件，并以 pi 进程的权限运行 shell 命令。扩展是 TypeScript 模块，以相同的权限运行。包安装、shell 命令、语言服务器、测试命令和其他开发工具的行为与普通本地进程无异。

这是有意为之的设计。Pi 旨在操作本地源代码树、调用项目工具链，并与用户现有的开发环境集成。一个部分的进程内沙箱很容易被误解为一种安全边界，但实际上它仍然依赖于主机 shell、文件系统、包管理器、凭据和扩展代码。真正的隔离需要来自操作系统或虚拟化/容器边界。

项目信任仅仅是一种输入加载保护机制。它可以防止仓库在你批准之前悄悄更改 pi 的设置或扩展。它不能使不受信任的代码、不受信任的提示或不受信任的模型输出变得安全。来自仓库文件、注释、文档、上下文文件或构建输出的提示注入是预期中的本地代理风险，pi 无法可靠地防止这类风险。

## 运行不受信任或无人监控的工作

对于不受信任的仓库、你不打算密切监控的生成代码，或无人值守的自动化任务，应在受限环境中运行 pi。使用容器、虚拟机、微虚拟机、远程沙箱或策略控制的沙箱，并仅提供任务所需的文件和凭据。

常见模式记录在[容器化](containerization.md)中：

- 在 OpenShell 或 Docker 中运行整个 `pi` 进程
- 在主机上运行 pi，同时将内置工具的执行路由到 Gondolin 微虚拟机中
- 仅挂载代理应访问的工作区路径
- 除非容器需要访问主机会话、设置和凭据，否则避免挂载主机的 `~/.pi/agent`
- 传递所需的最小 API 密钥，或使用短期有效的凭据
- 在任务不需要网络访问时限制网络访问
- 在将结果复制回受信任系统之前，先审查差异和输出

如果你以读写方式绑定挂载主机工作区，容器或虚拟机内部的写入操作仍然可以修改主机文件。如果需要更强的防护以避免意外写入，请使用只读挂载，或在沙箱内外复制文件。

## 报告安全问题

要报告安全问题，请遵循仓库的[安全策略](https://github.com/earendil-works/pi-mono/blob/main/SECURITY.md)。请勿为安全敏感的报告创建公开 issue。

预期中的本地代理行为、缺乏内置沙箱、来自不受信任内容的提示注入，以及用户安装的扩展或技能的行为，一般不属于安全边界范围，除非报告展示了真实的权限边界绕过，或说明了 pi 授予了本地用户原本未拥有的访问权限。
